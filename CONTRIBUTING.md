# Contributing

## Release automation

Releases are automated with two GitHub Actions workflows.

### 1) Release Prepare (manual)

Run **Release Prepare** from the Actions tab on `master`.

Inputs:
- `release_type`: `patch`, `minor`, or `major`
- `version`: explicit `X.Y.Z`

Provide exactly one input.

What it does:
- bumps `package.json` version
- validates tag/release guardrails
- runs tests and package build
- creates VSIX and validates version alignment
- commits bumped version to `master`
- creates and pushes `vX.Y.Z` tag
- creates/updates a **draft** GitHub release with autogenerated notes and attached VSIX

After this, edit release notes in the draft release UI if human-written changes are needed.

### 2) Release Publish (on release published)

When the draft release is published, **Release Publish** runs automatically and:
- downloads VSIX from the release
- publishes VSIX to Visual Studio Marketplace
- publishes VSIX to Open VSX
- verifies VSIX remains attached on GitHub release page (re-uploads if missing)

### Required secrets and permissions

Configure repository/environment secrets:
- `VSCE_PAT`: Visual Studio Marketplace publishing token
- `OVSX_PAT`: Open VSX publishing token

The publish job uses GitHub Actions environment `release`.
Protect this environment with required reviewers to gate the actual publication step.

### Rollback guidance

If publish fails:
1. Keep the GitHub release in draft (or unpublish if already published) while fixing credentials/config.
2. Verify release asset and tag version alignment (`vX.Y.Z` and `*-X.Y.Z.vsix`).
3. Re-run publish by publishing the draft release again (or re-run failed workflow after fixes).
4. If a marketplace was partially published, deprecate or replace the faulty version per marketplace policy, then publish a corrected patch release.

### Optional future enhancement

Automate `CHANGELOG.md` updates from release notes/conventional commits and inject curated changelog text into the generated release body.
